# 슈퍼컴퓨팅센터 사이트 기능 및 운영 방식 조사 보고서

대상: https://su-pa-fa-mu.com/  
갱신 기준일: 2026년 11월 2일, 한국시간 (운영 구조·오류 수정·Docker 제출본 갱신판)  
문서 성격: 프로젝트 채팅의 완료 기록, Spaceship MCP의 최신 운영 소스·공개 콘텐츠·설정 조회, 이전 관리자 브라우저 확인 기록과 새 Docker 검증 결과를 대조한 구현 현황 보고서. 운영 사이트에서 실제 회원 탈퇴·전체 심사·백업 복원을 수행한 인증 문서는 아니다. 과거 측정값은 해당 날짜를 유지한다.

## 핵심 요약

su-pa-fa-mu.com은 WordPress 기반의 슈퍼컴퓨팅센터 시험 운영 포털이다. 회원 이메일 인증, 이용신청, HWPX·HWP·PDF 출력, 서명 파일 제출, 관리자 심사 상태 관리, 첨부 검사, KBoard Q&A·승인 회원 포럼, FAQ와 Gemini 안내 챗봇을 연결한다. 실제 계산 서버 계정 발급·자원 할당·계산 실행은 별도 범위다.

**“시험 운영 사이트입니다. 실제 접수는 진행하지 않습니다.”**라는 안내를 유지한다. 운영 실적이 아닌 기능 구현·시연 및 운영 기반 구축 성과로 설명한다.

11월 2일 운영 설치본은 **WordPress 7.1.4**, PHP CLI **8.2.35**, 테마 **HPC Portal Pages 0.7.0**, 업무 플러그인 **HPC Feature Lab 0.6.0**이다. 일반 플러그인 **23개(활성 18·비활성 5)**와 **화면 문구용 MU 플러그인 1개**가 있다. 같은 버전 표기에도 후속 코드 변경이 있어 파일 기준으로 제출본을 갱신했다. [E23]

공지·일정·알림판·FAQ의 등록·편집 기능은 **HPC Content 1.0.0**으로 독립했다. 안내 본문은 WordPress 페이지에서, 728개 공통 문구는 **설정 → 센터 화면 문구**, 5개 메뉴 위치는 **모양 → 메뉴**에서 관리한다. 전용 페이지 편집 플러그인은 비활성화했다. [E24–E26]

기존 조사에서 확인한 **챗봇의 KBoard 검색 누락, JPEG 첨부 탈퇴 처리 불일치, KBoard 탈퇴 정리 누락**은 후속 코드에 반영되었다. 공개 Q&A의 비회원 접근 충돌, 챗봇의 공지·일정 출처 연결도 수정했다. 실제 운영 계정 삭제나 전체 심사·복원 시험까지 완료했다는 의미는 아니다. [E24]

공개 FAQ 30건, 공지 2건, 일정 3건, 알림판 2건을 새 초기 데이터로 담았다. **2026-11-02 Docker 제출본**은 최신 소스·페이지·FAQ·문구·메뉴를 반영하며, 운영 회원·신청·문의·첨부·API 키는 제외한다. 이전 10월 28일 제출본은 별도 보존한다. 로컬 검증 범위는 제출본의 `docs/검증결과.md`에 기록한다. [E27]

## 사용자와 권한에 따른 운영 방식

| 사용자 유형 | 이용·관리 범위 | 제한 또는 조건 |
|---|---|---|
| 비회원 | 센터 소개, 공지, 신청 안내, 교육 안내, 모의 실습, FAQ, 이용 수칙, 공개 Q&A·공개 자료 챗봇 등 | 이용신청 접근 시 마이페이지 로그인 주소로 HTTP 302 응답 확인 |
| 이메일 인증 전 회원 | 로그인 후 인증 진행 | 신청·문서 등 핵심 서비스는 이메일 인증 필요 |
| 인증 일반 회원 | 본인 신청 작성·조회·수정·제출, 공개 여부를 선택하는 Q&A 작성, 마이페이지 | 타인 신청·비공개 문의는 접근 대상에서 제외. 공개 문의는 누구나 열람 가능 |
| 선정 회원 | 일반 회원 기능 및 이용자 포럼 | 인증 완료 및 `selected` 신청 보유, 탈퇴 처리 중이 아닐 것 |
| 관리자 | 전체 신청 확인, 심사 상태 변경, 문의 답변, 양식·공지·일정·알림판 관리, 운영 점검 | 핵심 관리 기능은 `manage_options` 권한 기준 |

WordPress에는 관리자·편집자·글쓴이·기여자·구독자 기본 역할이 등록되어 있다. 다만 ‘전문가’, ‘위원회’는 신청 상태 이름으로 구현되어 있으며 별도 심사자 역할·개별 심사위원 배정 체계는 확인되지 않았다. 현재 코드는 관리자가 단계와 사유를 입력하는 방식이다. 실제 담당 부서와 결재 책임자는 운영자 확인이 필요하다. [E1, E4, E5, E6]

### 회원가입·로그인

1. 회원가입 화면에서 이메일과 동의 정보를 입력하고 인증 메일을 요청한다.
2. 30분 동안 유효한 일회용 인증 링크를 통해 가입 절차를 계속한다.
3. 신규 가입자는 이름과 15~128자의 비밀번호를 설정한다.
4. WordPress 구독자 계정을 생성하고 인증 이메일에 대응하는 확인값과 인증 시각을 기록한다.
5. 이메일 또는 사용자명으로 로그인하며, 신청 기능에서는 인증 여부를 다시 확인한다.

인증 요청에는 이메일·IP·사이트 단위 요청 횟수 제한이 구현되어 있다. 이미 인증된 이메일에는 기존 계정 이용 및 비밀번호 재설정 안내를 보내도록 되어 있다. 비밀번호와 로그인 세션은 WordPress가 관리한다. 인증 메일 발송 실패 시 관리자 알림을 남기는 코드가 있으며, 조사 시 해당 실패 기록 옵션은 확인되지 않았다. 이것만으로 메일 수신 성공을 입증할 수는 없다. [E4, E7]

### 이용신청과 심사

| 단계 | 처리 주체 | 처리 내용 | 결과 |
|---|---|---|---|
| 작성·저장 | 인증 회원 | 기관·연락처·연구 목적·자원 요구량·계정 희망안·동의 항목 입력 | ‘작성 중’ 신청 저장 |
| 문서 확인 | 신청인 | 저장 내용으로 HWPX·HWP·PDF 다운로드 및 서식 확인 | 다운로드만으로 제출되지 않음 |
| 서명 및 제출 | 신청인 | 서명·날인 신청서 필수 첨부, 기관 공문 또는 별도 발송 정보, 선택 추가자료 | ‘제출 완료’, 시험용 접수번호 부여 |
| 첨부 검사 | 서버 정기 작업 | 파일 무결성과 악성코드 검사 | 통과 전 첨부 다운로드 차단 |
| 접수 확인 | 관리자 | 제출 내역 검토 및 처리 사유 입력 | ‘접수 확인’ 또는 ‘보완 요청’ |
| 전문가 검토 | 관리자 권한 계정 | 검토 단계 진행 또는 보완·미선정 처리 | ‘전문가 검토’ 이후 허용 상태로 이동 |
| 위원회 심의 | 관리자 권한 계정 | 심의 결과와 사유 입력 | ‘선정’, ‘미선정’ 또는 ‘보완 요청’ |
| 결과 확인 | 신청인 | 신청 상세에서 상태·처리 사유·이력 확인 | 선정 신청 보유 시 포럼 접근 조건 충족 |

주요 상태 흐름은 다음과 같다.

```text
작성 중 → 제출 완료 → 접수 확인 → 전문가 검토 → 운영위원회 심의 → 선정 / 미선정
            │             │             │                  │
            └─────────────┴─────────────┴──────────────────┴→ 보완 요청 → 재제출

제출 완료·접수 확인 → 신청인 수정 시작 → 수정 중 → 새 서명 파일 첨부 → 재제출
전문가 검토 단계에서는 미선정으로 직접 변경도 가능
```

제출 완료·접수 확인 단계에서는 본인이 수정을 시작할 수 있다. 이후에는 새 서명 문서를 첨부해 다시 제출해야 한다. 심사·결과 확정 단계의 변경은 Q&A로 문의하도록 안내한다. 관리자 변경은 허용된 단계만 가능하고, 사용자에게 공개할 사유가 필수다. 코드에는 처리 버전 비교와 데이터베이스 트랜잭션이 있어 동시에 열린 화면의 중복 변경을 방지하려는 구조가 있다.

10월 28일 조사 당시 활성 양식은 ‘기존 2027년 상반기 신청서’ 1종이다. 기본 양식의 사용기간은 2027년 1월 1일~6월 30일로 고정되어 있으며 시험 접수번호는 `HPC-TEST-` 접두어를 사용한다. 신청서의 유상·무상 구분은 수집 항목이며 온라인 결제 구현 근거는 확인되지 않았다. [E3, E5, E8]

### 신청 문서와 첨부파일

HWPX 양식에 신청 데이터를 채우고 서버의 RHWP 변환 도구로 HWP·PDF를 생성한다. 생성 파일은 신청 데이터와 양식 정보를 반영한 경로에 저장하여 다시 사용할 수 있는 구조다. 10월 28일에 조회한 출력 점검 기록에는 2026년 10월 19일 HWPX·HWP·PDF 생성 성공이 남아 있다.

작성 중 미리보기는 인증·요청 검증 후 임시 HWPX를 생성해 반환하고 임시 파일을 정리하는 방식으로 구현되어 있다. RHWP 브라우저 편집기와 WebAssembly 파일이 함께 배포되어 있다.

서명 신청서는 HWP·HWPX·PDF, 추가자료는 PDF·HWP·HWPX·JPEG 계열을 허용한다. 파일당 10MB 제한이며 서명 신청서·기관 공문·추가파일은 각각 별도 입력 항목이다. 코드에서 확장자뿐 아니라 실제 파일 형식도 검사한다. 이전 제출 파일과 처리 이력을 보존한다. [E5, E8, E9]

### 문의·포럼·탈퇴

**Q&A:** 현재 화면과 저장은 KBoard가 담당하고, HPC KBoard Bridge가 기존 이메일 인증·사용자 권한과 연결한다. 인증 회원은 작성할 때 공개·비공개를 선택하며 신규 글의 기본값은 비공개다. 공개 글은 누구나 볼 수 있고 비공개 글은 작성자와 관리자만 볼 수 있다. 관리자가 비공개로 전환한 글은 작성자가 임의로 다시 공개할 수 없도록 잠금 처리가 있다.

관리자는 **게시판 관리 → 문의 Q&A**에서 검색·본문 수정·답변·비공개 전환·숨김을 처리한다. 새 답변 또는 변경된 답변을 저장하면 작성자의 가입 이메일로 알림을 보내며, 메일에는 답변 본문 대신 확인 링크를 제공한다. 동일 답변의 중복 발송 방지와 실패 시 5분 뒤 재시도(최대 3회 시도) 코드가 있다. 10월 31일 작업 기록에는 테스트 메일의 **발송 요청 성공**이 남아 있으나 실제 수신함 도착까지 확인한 기록은 아니다. 이번 갱신에서는 운영 메일을 발송하지 않았다. [E17, E18]

**이용자 포럼:** KBoard와 KBoard 댓글을 사용하며 기존 `hpcf_allowed()`의 이용 승인 판정을 연결했다. 관리자는 **게시판 관리 → 포럼 관리**에서 글을 검색·편집·숨김 처리한다. 기존 작업 기록에는 글·댓글 작성 및 관리자 편집 확인이 남아 있다. 10월 31일 관리자 현황은 Q&A·포럼 각각 0건이며, 기존 시험 글은 사용자 요청으로 운영 목록에서 제외하고 복구용 자료를 보관한 것으로 기록되어 있다. 실제 계산 서버 계정 활성화와의 연동을 뜻하지 않는다.

**회원 탈퇴:** 비밀번호·동의·진행 중 신청 제한 확인 후 정기 작업으로 신청·파일·계정을 정리한다. 11월 2일 JPG/JPEG 확장자를 정리 대상에 추가했고, 본인 KBoard 글·댓글의 익명화와 첨부 정리를 연결했다. 타인의 답글은 보존한다. 운영에서 실제 탈퇴를 실행하지 않았으므로 최종 보유기간·백업본 정리와 전체 절차는 별도 검증 대상이다. Docker 새 설치에서는 기존 정리 코드가 참조하는 옛 게시판 저장소를 빈 호환 테이블로 생성한다. [E24, E27]

**HPC Content**가 공지·일정·알림판·FAQ의 콘텐츠 유형, 편집 항목과 검증을 담당한다. 테마는 방문자 레이아웃·달력 등의 표시를 담당한다. 따라서 테마를 교체해도 원본과 등록 기능은 별도 플러그인에 남지만, 기존 화면 디자인이 자동 유지되는 것은 아니다. FAQ 원본 등록은 챗봇과도 분리되었다. [E25]

**HPC Screen Copy**는 자동 로드되는 MU 플러그인이며, 실제 문구는 데이터베이스 옵션에 저장된다. 소스만 복사하면 문구를 재현할 수 없으므로 Docker에는 해당 옵션을 선별 포함했다. 메뉴 검색·옆 메뉴·그룹 경로는 상단 메뉴를 공통 기준으로 사용한다. 메뉴에서 페이지를 빼는 것은 접근 권한 차단과 다르다. [E26]

예전 **HPC 설치** 메뉴, 일회성 설치·배포 도구와 옛 Q&A·포럼 작성 화면은 정리했다. **HPC 운영 점검**은 유지한다. 구 게시판 주소는 현재 페이지로 연결하고, 구 작성 요청은 받지 않는다. `hpc-page-content`는 비활성 보관, `hpc-forum-update`는 설치 플러그인 목록에서 제거했다. [E24]

FAQ는 홈페이지 이용 6, 접속·인증 4, 자원·작업 3, 소프트웨어 3, 데이터·저장공간 3, 센터 소개 11건으로 구성한다. 검색·분류·펼치기·모두 접기·질문별 링크를 제공한다. 확인 필요 표시와 2025년 출처 표시를 유지한다.

### AI 챗봇의 현재 동작과 범위

서버가 질문의 단어와 일치하는 자료의 문단을 선별하고 **Gemini 3.1 Flash-Lite**가 근거를 바탕으로 답변을 생성한다. 배포 코드의 호출 모델 식별자는 `gemini-3.1-flash-lite`다. 이는 현재 사이트 구성값이며 외부 제품의 최신 모델·가격을 조사한 결과는 아니다.

1. 질문은 최대 500자, 이전 대화는 전달하지 않는 단일 질문 방식이다.
2. 공개 페이지·게시글·공지·일정·FAQ와 공개 KBoard Q&A 본문·관리자 답변을 읽는다. 포럼은 승인 회원 권한과 제공 설정을 확인한다. 신청·신청현황·마이페이지·Q&A·포럼 페이지 자체는 일반 공개 자료 수집에서 제외한다.
3. 본문을 최대 500자 단위 문단으로 나누고 제목·본문의 키워드 일치도와 FAQ 가중치로 순위를 정한다. 벡터·임베딩 기반 의미 검색은 확인되지 않았다.
4. 최대 5개 문단, 같은 글 최대 2개, 합계 2,200자 이내 본문을 모델에 전달한다. 관리자에 표시된 ‘약 4,000토큰’은 문맥 목표이며 실제 고정 입력량이 아니다. 최대 출력 설정은 768토큰이다.
5. 근거 부족·연결 오류·사용 한도 도달 시 Q&A와 설정된 연락처를 안내한다. 현재 연락처에는 임시 표시가 설정되어 있다.
6. 답변의 출처 ID를 서버가 검증하고 현재 공개 범위·수정 상태를 다시 확인한 뒤 원문 링크를 제공한다.

관리자 화면에서 API 키 설정됨, 하루 호출 한도 **100회(UTC 기준)**, 포럼 자료 제공 허용 상태를 확인했다. 배포 코드에는 질문 간격 5초와 일일 누적 토큰 기준 제한도 있다. 최근 사용량은 UTC 10월 30일 11회·입력 4,943·출력 1,003·연결 실패 0, 10월 31일 1회·입력 427·출력 97·실패 0이었다. 이 집계와 기존 실제 답변 확인 기록은 구분하며, 이번 조사에서 새 답변 호출은 하지 않았다. 질문·대화 원문을 저장하지 않는 자체 사용량 테이블 구조이나 외부 제공자의 보관 정책까지 확인한 것은 아니다. [E18]

**KBoard 연동 수정:** 11월 2일 공개 Q&A 본문·관리자 답변과 승인 회원에게 허용된 포럼 본문을 직접 검색하도록 변경했다. 비공개·휴지통 자료를 제외하고 답변 직전에 권한과 변경 상태를 다시 확인한다. 구 공개 Q&A 가져오기·초기 설치 코드는 제거했다. 공지 출처는 공지 상세, 일정 출처는 해당 날짜 달력으로 연결하며, 작업 기록에서 공지 2건·일정 3건 연결 응답을 확인했다. [E24, E25]

이미지 속 글자와 PDF·HWP 첨부 내용을 자동 추출하는 검색은 구현 완료로 보고하지 않는다. 질문과 선별 문단은 Google AI로 전송하며 개인 신청서·비공개 연구자료 입력을 피하도록 안내한다. Docker에는 운영 API 키가 없고, 키가 없을 때의 검색·안내와 실제 AI 생성은 구분한다.

## 운영상 추가 확인 사항

1. **정식 운영 정책:** 모집 기간·이용 자격·담당 부서·연락처·처리기한·보유기간을 확정해야 한다. Privacy Policy는 초안이다.
2. **심사 책임·승인 이후 업무:** 전문가·위원회는 관리자 상태 처리 방식이다. 심사위원별 배정·결재 분리, 계산 서버 계정·자원·만료·사용량·결제 연동은 별도 범위다.
3. **알림:** Q&A 답변 이메일의 실제 외부 수신·재시도와 신청 접수·선정 결과 알림은 별도로 검증해야 한다. Mailpit 성공은 운영 이메일 전달 성공을 뜻하지 않는다.
4. **챗봇:** KBoard 검색 및 출처 연결 수정은 반영되었다. 공개 첨부문서 추출, 검색 정확도, 실제 API 응답 품질·비용·외부 제공자 보관 정책은 별도 확인 대상이다.
5. **탈퇴:** JPG/JPEG 형식 불일치와 KBoard 정리 누락은 수정했다. 운영 회원을 실제로 삭제하지 않았으며 최종 정리·재시도·백업본 보유기간을 추가 검증해야 한다.
6. **백업·복구:** 비공개 문서 저장소, 문구·메뉴 옵션, KBoard·챗봇 자료가 백업되고 실제 복원되는지 검증해야 한다.
7. **교육·자료 최신성:** 교육 수료 이력과 실제 계산 실행은 완료 기능이 아니다. FAQ의 확인 필요·2025년 자료 표시를 유지한다.
8. **운영과 시연 구분:** Docker에는 운영 개인정보·서비스 인증정보가 없다. Pro 인증과 실제 AI 호출은 자동 복제되지 않는다. 정확한 로컬 재검증 범위는 제출본 검증 문서를 기준으로 한다.

## RHWP 오픈소스 도입 및 활용

한글 문서 처리에는 [edwardkim/rhwp](https://github.com/edwardkim/rhwp)의 오픈소스를 활용했다. RHWP는 Rust·WebAssembly 기반 HWP/HWPX 뷰어·편집기이며 원본 저장소는 MIT 라이선스를 표시한다. 사이트에는 브라우저용 SDK·편집 화면·문서 처리 모듈을 배치하고 맞춤 플러그인에서 신청 업무에 연결했다. WordPress 설치 플러그인 23개와 별도로, HPC Feature Lab 내부에서 활용하는 구성요소다. [E13]

| 활용 항목 | 사이트에 연결한 방식 | 사용 목적 |
|---|---|---|
| 관리자 웹 문서 편집기 | SDK의 `createStudio`로 자체 배포한 편집 화면을 삽입. 기존 HWP·HWPX 열기 또는 빈 문서 생성 후 HWPX로 내보내기 | 관리자가 브라우저에서 신청 양식 작성·수정 |
| 문서와 신청 항목 연결 | 편집 위치에 `[[HPC:항목ID]]` 표시를 넣고 항목명·입력 방식·필수 여부 설정. HWPX와 설정을 서버에 보내 새 양식 초안으로 저장 | 문서 입력 위치와 웹 신청 항목 연결. 원래 양식은 유지하고 시험 출력·적용 절차로 이동 |
| 작성 중 출력 미리보기 | 서버가 입력값을 반영한 임시 HWPX를 반환하면 브라우저 RHWP 모듈이 페이지별 SVG로 표시 | 신청서 출력 모양 확인. 코드상 입력을 멈춘 뒤 약 650ms 후 갱신, 최대 20쪽 지원 |
| 서버 문서 변환 | 맞춤 코드로 작성한 HWPX를 서버 변환 도구의 `convert`로 HWP, `export-pdf`로 PDF 생성 | 동일 신청 내용을 HWPX·HWP·PDF로 다운로드 제공 |

RHWP는 문서 열기·편집·렌더링·형식 변환에 활용했다. 회원 인증, 신청 데이터 저장, 문서 입력 표시와 웹 항목 연결, 양식 초안·버전 관리, 다운로드 권한 및 심사 절차는 사이트의 맞춤 코드로 구현했다. 따라서 개발 성과는 **“RHWP 기반 웹 문서 편집·미리보기·변환 기능을 신청 포털에 통합”**으로 설명한다.

미리보기는 브라우저에서 표시하지만 입력값을 사이트 서버에 전송해 임시 문서를 생성하는 구조다. 미리보기 자체가 신청 저장·접수를 수행하지는 않는다. 브라우저와 서버의 글꼴 차이로 최종 PDF의 줄바꿈이 달라질 수 있다는 안내도 포함되어 있다.

이전 조사에서 배포된 `editor.php`, `editor.js`, `live-preview.js`, `documents.php`의 연결을 확인했다. 10월 28일 조사 당시 활성 양식은 기존 방식의 양식 1종이므로 웹 편집기로 새 양식을 만들어 운영에 적용한 실적까지 확인된 것은 아니다. 도입한 RHWP의 정확한 버전·커밋, 원본 대비 변경 범위 및 배포본의 라이선스 고지 보존 여부는 이번에 대조하지 않았다. 편집·저장·변환의 전체 사용자 동작 시험도 별도다.

보고서에 바로 사용할 문안:

> HWP/HWPX 문서 처리 오픈소스 RHWP를 도입하여 관리자용 웹 문서 편집기, 신청서 작성 중 출력 미리보기, HWP·PDF 변환 기능을 포털에 통합하였다. 문서 편집 결과와 신청 입력 항목을 연결하고 새 양식 초안으로 저장하는 기능은 맞춤 개발하여, 문서 양식 관리와 온라인 신청 절차가 연계되도록 구성하였다.

### Docker 제출 환경에 추가한 구성요소

| 구성요소 | 로컬 재현 환경에서의 역할 |
|---|---|
| MariaDB 10.11 | 새 회원·신청·콘텐츠를 저장하는 로컬 데이터베이스 |
| Apache | localhost 요청을 받아 WordPress와 PHP 실행 |
| Mailpit | 외부 발송 없이 회원가입 인증 메일을 확인하는 테스트 메일함 |
| FreshClam | ClamAV 악성코드 검사 정의 파일 다운로드·갱신 |

이 표는 Docker 제출 환경에서 확인한 구성이다. 운영 호스팅의 데이터베이스·웹서버 제품과 동일하다고 단정하지 않으며, 운영 서버의 검사 정의 갱신 방식도 별도로 확인해야 한다. Docker는 재현 환경을 구성하는 도구로 사용했으며 Docker Desktop 전체를 하나의 오픈소스 프로그램으로 분류하지 않는다.

보고서용 문안:

> WordPress와 PHP를 기반으로 포털을 구축하고, RHWP의 한글 문서 편집·변환 기능과 ClamAV의 첨부파일 검사 기능을 통합하였다. 이메일 전송과 문서 출력에는 PHPMailer 및 Noto CJK 글꼴 등 기존 오픈소스 구성요소를 활용하였다. 회원 인증·신청·심사 절차는 자체 개발 플러그인으로 연결하였으며, 제출용 환경에는 MariaDB·Apache·Mailpit 등을 구성하여 로컬에서 재현할 수 있도록 하였다.

## 프로젝트 보고서용 기술 문안

본 프로젝트는 WordPress 기반 슈퍼컴퓨팅센터 시험 운영 포털을 구축하고 전용 테마와 맞춤 플러그인을 통해 안내·신청·이용자 지원 기능을 통합하였다. 이메일 인증 기반 회원가입, 신청서 작성 및 HWPX·HWP·PDF 출력, 서명 문서 제출, 접수·검토·심의 상태 관리와 첨부파일 검사 구조를 구현하였다. 문서 편집·미리보기·변환에는 RHWP를 활용하였다.

후속 개발에서는 KBoard에 회원 권한을 연결하여 공개·비공개 Q&A, 관리자 답변·이메일 알림, 승인 회원 포럼을 구성하였다. FAQ 30건 검색·분류와 Gemini 안내 챗봇을 통합하고 공개 Q&A·관리자 답변·권한 허용 포럼을 검색 자료에 연결하였다. 콘텐츠 원본 관리는 독립 플러그인으로 분리하고, 안내 본문·728개 화면 문구·5개 메뉴 위치를 관리자에서 편집할 수 있도록 개선하였다. 실제 계산 서버 운영 연동은 별도 개발 범위다.

11월 2일에는 최신 운영 소스와 공개 콘텐츠를 반영한 Docker 제출본을 갱신하였다. 운영 개인정보와 인증정보를 제외하고 새 관리자·빈 업무 저장소를 생성하며 메일은 로컬 Mailpit으로 보낸다. 기존 10월 28일 검증 기록과 이번 재검증 범위를 구분하여 기록한다. 사이트 전체는 실제 접수를 수행하지 않는 개발·시연 환경이다.

### 구현 과정에서의 어려움과 개선

WordPress는 콘텐츠 관리 시스템이며 플러그인은 기본 기능을 확장하는 도구다. 모든 기능이 특정 페이지 안에만 배치되거나 서버에서만 실행되는 것은 아니다. 필요한 기능에 적합한 기존 도구를 선정하고 사이트 전체의 권한·데이터·화면과 연결하는 과정이 주요 개발 과제였다.

문서 처리는 RHWP, 게시판은 KBoard 등 기존 구성요소를 활용하고, 신청·심사·이메일 인증·공개 범위·답변 알림은 맞춤 코드로 연결하였다. 이 과정에서 새 기능을 만드는 작업뿐 아니라 기존 기능과 새 저장 구조의 호환, 관리자 편집 동선, 검색 자료의 일관성을 관리하는 작업도 필요했다. 생성형 AI를 활용하더라도 기존 도구로 해결할 범위와 별도 개발·검증이 필요한 범위를 먼저 나누는 것이 중요하다는 점을 확인하였다. 이 내용은 프로젝트의 구현 과정 정리 채팅과 실제 플러그인 구성을 반영한다. [E20]
